# 0004. Rule-based extraction first, with optional LLM refinement and cloud OCR

- Status: accepted
- Date: 2026-10-29

## Context

Most supplier invoices arrive as PDFs generated by billing systems, with a text layer. Sending every
document to a cloud OCR service or an LLM costs money per page, adds latency and an external
dependency, and gives non-deterministic results that are hard to test. Scanned documents, though, do
need OCR.

## Decision

An `Extractor` interface with two implementations, chosen by configuration:

- `PdfTextExtractor` (default): pdfplumber text and ruled tables, then a parser that recognises
  labelled fields, line items and totals, with per-field confidence and cross-checks between fields.
- `AzureDocumentIntelligenceExtractor`: the `prebuilt-invoice` model, for scans and images.

Either can be wrapped with LLM refinement, which runs only when overall confidence is below a
threshold and may only fill fields that were missing or weak. Every result records the method used
(`pdf_text`, `pdf_text+llm`, …) and per-field confidence, and low confidence alone blocks
auto-approval.

## Consequences

- The common case is free, fast, deterministic and fully covered by tests (three different invoice
  layouts are rendered and parsed in the test suite).
- Scans are supported without changing the pipeline, and fail safe (to review) when OCR isn't enabled.
- LLMs improve recall on unusual layouts without being trusted for values the parser already read
  confidently.
- New layouts may need parser rules. The confidence score and the review queue make such gaps visible
  instead of silently wrong.
